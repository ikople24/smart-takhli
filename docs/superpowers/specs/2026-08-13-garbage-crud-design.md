# ระบบตารางเก็บขยะ — แก้ไขตารางจากหน้าแอดมิน (M6) · Design Spec

**วันที่:** 2026-08-13
**ต่อจาก:** M1–M3 (PR #116) และ M4–M5 (PR #118) — ทั้งสอง PR ยังไม่ merge
**Branch:** `feat/garbage-crud` แตกจาก `feat/garbage-ui` (stacked ชั้นที่ 3)

## ปัญหาที่ต้องแก้

M4–M5 ทำหน้าแอดมินแบบอ่านอย่างเดียว ทางเดียวที่จะเพิ่ม/แก้ตารางคือแก้ `data/garbage/schedule-seed.json` ด้วยมือแล้วรัน `scripts/seed-garbage.mjs` — เป็นงานของโปรแกรมเมอร์ ไม่ใช่งานที่เจ้าหน้าที่กองสาธารณสุขทำเองได้ **ระบบจึงยังไม่ครบวงจร**: ทุกครั้งที่ตารางเปลี่ยนต้องกลับมาหาคนเขียนโค้ด

จุดที่ทำให้เห็นชัด: ตารางวันพุธ–อาทิตย์ยังว่าง 5 วัน พอกองสาธารณสุขส่งตารางมาก็ยังกรอกเข้าระบบเองไม่ได้ · และสาย R5–R7 ที่ติดป้าย "รอตรวจสอบ" ก็ปลดป้ายเองไม่ได้เพราะแก้ชื่อจุดไม่ได้

## ขอบเขต (ตัดสินร่วมกับเจ้าของโปรเจกต์)

| เรื่อง | ที่เลือก |
|---|---|
| ระดับการแก้ | งานมอบหมายรายวันเต็มรูปแบบ (เพิ่ม/แก้/ลบ) |
| แหล่งความจริง | **UI เป็นหลัก** — seed เหลือเป็นแค่ bootstrap ตอน DB ว่าง |
| ประวัติการแก้ | ทับข้อมูลเดิม ไม่เก็บหลายเวอร์ชัน — เก็บร่องรอยใน audit log แทน |
| สายและจุดเก็บ | แก้ได้ด้วย (ชื่อสาย, เพิ่ม/ลบ/เรียงจุด, ปลดป้ายรอตรวจสอบ) |

**ไม่ทำรอบนี้ (YAGNI):** ย้อนดูตารางเก่า/versioning UX · แก้ทะเบียนรถและรายชื่อชุมชน (ยังผ่าน seed) · แผนที่เส้นทาง (M7) · export โปสเตอร์ · แจ้งเตือน LINE ก่อนรถถึง · ตารางซ้ำอัตโนมัติ (copy วันจันทร์ไปวันอังคาร) — ไว้รอบหน้าถ้าเจ้าหน้าที่ขอ

## หลักการที่ตัดสินใจไว้แล้วและต้องยึด

### 1. `effectiveFrom` คงที่ที่ baseline เดียว

เมื่อไม่ทำ versioning งานมอบหมายทุกตัวใช้ `effectiveFrom = 2026-01-01T00:00:00+07:00` (ค่าเดียวกับที่ seed ใช้อยู่) และ `effectiveTo = null` เสมอ → resolver มองเห็นทุกตัวในทุกวันที่ค้นหา สิ่งที่อยู่ใน DB คือตารางที่ใช้จริง จบ

**เหตุผลที่ไม่ใช้ "วันนี้" เป็น effectiveFrom:** เจ้าหน้าที่กรอกตารางวันพุธในวันพฤหัสบดี แล้วเปิดดูสัปดาห์ปัจจุบันจะไม่เห็นงานที่เพิ่งกรอก (เพราะวันพุธที่ผ่านมาอยู่ก่อน effectiveFrom) — สับสนโดยไม่จำเป็น

ฟิลด์ทั้งสองยังอยู่ในสคีมาและ resolver ยังกรองด้วยมันเหมือนเดิม (เทส M1–M3 ยึดพฤติกรรมนี้ไว้) เก็บไว้รองรับ versioning ในอนาคต · ค่า baseline ต้องประกาศไว้ **ที่เดียว** ใน `lib/garbage/constants.ts` และ `scripts/seed-garbage.mjs` อ้างค่าเดียวกันพร้อมคอมเมนต์กำกับ (สคริปต์เป็น `.mjs` import `.ts` ไม่ได้ จึงต้องคัดลอกค่าและกำกับให้ชัดแบบเดียวกับที่ทำกับรายการ index อยู่แล้ว)

### 2. seed script เปลี่ยนเป็น insert-only

ตอนนี้ `scripts/seed-garbage.mjs` ใช้ `$set` ทุกฟิลด์ = รันซ้ำจะทับค่าที่เจ้าหน้าที่แก้จาก UI ทั้งหมด ต้องเปลี่ยนเป็น:

- ใช้ `$setOnInsert` สำหรับทุกฟิลด์ → เอกสารที่มีอยู่แล้วจะไม่ถูกแตะเลย
- พิมพ์สรุปให้ชัดว่าเพิ่มใหม่กี่ตัว **ข้ามไปกี่ตัวเพราะมีอยู่แล้ว**
- แก้คอมเมนต์หัวไฟล์: เลิกบอกว่า seed คือ source of truth เปลี่ยนเป็น "ใช้ตั้งต้นตอน DB ว่างเท่านั้น ข้อมูลจริงแก้จาก /admin/garbage"
- `data/garbage/schedule-seed.json` จะ drift จาก DB เป็นเรื่องปกติและตั้งใจ — ระบุไว้ในเอกสารโมดูล

### 3. กฎที่ต้องบังคับฝั่งเซิร์ฟเวอร์ (ไม่ใช่แค่ใน UI)

`assignmentSchema` ใน `lib/garbage/validators.ts` มีกฎภายในเอกสารครบแล้ว (วันหยุดห้ามมีสาย, แทนเบอร์ต้องระบุ `coverForRouteCode` และต้องมี `routeCode`, งานปกติต้องมีสาย, เวลาสิ้นสุดห้ามก่อนเวลาเริ่ม, `stopTimes` ห้ามย้อนกลับตามลำดับจุด) แต่ยังขาดกฎ **ข้ามเอกสาร** ที่ตอนนี้อยู่แต่ในสคริปต์ seed:

- **รถคันเดียวกันในวันเดียวกัน เวลาห้ามทับกัน** — ต้องคิวรีงานพี่น้อง `(weekday, truckNumber)` ตอน create/update แล้วตรวจ ไม่งั้นเจ้าหน้าที่จองรถซ้อนได้
- **`(weekday, truckNumber, shiftNo)` ต้องไม่ซ้ำ** — เพิ่ม unique index (ตรวจก่อนว่าข้อมูล 17 ตัวที่มีอยู่ไม่ชนกันเอง) คีย์นี้ตรงกับ filter ที่ seed ใช้ upsert อยู่แล้ว
- **`stopTimes[].seq` ต้องมีอยู่จริงในสายนั้น** — ตรวจตอนบันทึก

### 4. การแก้รายการจุดเก็บ — จุดที่ยากที่สุดของฟีเจอร์นี้

`assignment.stopTimes[].seq` อ้างถึง `route.stops[].seq` ถ้าเจ้าหน้าที่ลบจุดที่ 3 ของสาย R1 หรือสลับลำดับ เวลาของทุกงานที่ใช้สายนั้นจะเลื่อนผิดทั้งหมด — และผลคือ**ประชาชนเห็นเวลาผิด** ซึ่งร้ายกว่าไม่เห็นเวลา

**วิธีที่เลือก (ไม่ต้อง migrate สคีมา):** ตอนบันทึกรายการจุด ฝั่ง client ส่งลำดับใหม่ทั้งชุด โดยจุดเดิมพา `prevSeq` (ค่า seq ปัจจุบัน) มาด้วย จุดใหม่ส่ง `prevSeq: null` เซิร์ฟเวอร์:

1. คำนวณ seq ใหม่ 1..n ตามลำดับที่ส่งมา และสร้าง mapping `prevSeq → newSeq`
2. **เขียน `stopTimes` ของทุกงานที่ใช้สายนี้ก่อน** (แปลง seq ตาม mapping, ตัดเวลาของจุดที่ถูกลบออก)
3. **แล้วจึงเขียน `route.stops`**

ลำดับนี้สำคัญ: ถ้าขั้นที่ 3 ล้ม งานจะอ้าง seq ที่ยังไม่มีในสาย → `buildDaySchedule` หา `timeBySeq` ไม่เจอ → `atMin` เป็น null → หน้าเว็บแสดง "—" **ไม่แสดงเวลาผิด** (degrade อย่างปลอดภัย ไม่ต้องใช้ transaction)

ถ้าทำสลับลำดับ (เขียน route ก่อน) ผลคือเวลาผิดที่ดูเหมือนถูก — ยอมรับไม่ได้

### 5. ปลดป้าย "รอตรวจสอบ"

ฟอร์มแก้สายมีช่องติ๊ก "ตรวจสอบชื่อจุดกับกองสาธารณสุขแล้ว" → เซ็ต `needsVerification: false` เพื่อให้ loop เรื่อง R5–R7 ปิดได้เอง

### 6. audit log

ใช้ `lib/auditLogger.ts` ที่มีอยู่ ต้องเพิ่มค่าใน union ของไฟล์นั้น: action `garbage_assignment_created` / `garbage_assignment_updated` / `garbage_assignment_deleted` / `garbage_route_updated` และ resourceType `garbage_assignment` / `garbage_route` · บันทึก `before`/`after` ทุกครั้ง (คนแก้คือใคร เมื่อไร แก้อะไร) เพราะเลือกทับข้อมูลเดิม ร่องรอยจึงต้องอยู่ที่นี่ · เรียกหลัง operation สำเร็จเท่านั้น (ตัว logger เป็น fire-and-forget อยู่แล้ว ไม่โยน error กลับ)

## API ใหม่

ทุกตัวต้องผ่าน `requireGarbageAdmin()` จาก `pages/api/garbage/_auth.ts` (มีอยู่แล้ว ตรวจ Clerk → Mongo → `hasPermission` → กัน role ปลอม → เช็ค `isActive`/`isArchived`) และคืน `{ error }` ตามธรรมเนียมโมดูล

| Endpoint | Method | หน้าที่ |
|---|---|---|
| `pages/api/garbage/assignments/index.ts` | POST | สร้างงานมอบหมายใหม่ |
| `pages/api/garbage/assignments/[id].ts` | PUT / DELETE | แก้ / ลบงานมอบหมาย |
| `pages/api/garbage/routes/index.ts` | GET | รายการสายทั้งหมดสำหรับ dropdown (รวม `stops` เพื่อใช้ตั้งเวลารายจุด) |
| `pages/api/garbage/routes/[code].ts` | PUT | แก้ชื่อสาย, รายการจุด, `needsVerification` |

`GET /api/garbage/routes` **ต้องล็อกอิน** (ไม่เปิด public) เพราะเป็นข้อมูลตั้งต้นของฟอร์มแอดมิน ไม่ใช่ข้อมูลที่หน้าประชาชนต้องใช้ (หน้าประชาชนได้สายมาพร้อม `/week` และ `/search` แล้ว)

**การล้างแคช:** `/api/garbage/{schedule,week,search}` ตั้ง `s-maxage=300` ไว้ ดังนั้นหลังแก้ตาราง หน้าประชาชนอาจเห็นของเก่าได้ถึง 5 นาที · วันนี้ Railway ไม่มี CDN ข้างหน้าจึงไม่มีผลจริง แต่ต้องเขียนกำกับใน `docs/modules/garbage.md` ว่าถ้าวันไหนเอา Cloudflare มาวางต้องเพิ่มการ purge หรือลด s-maxage

## Validators ที่ต้องเพิ่ม

ใน `lib/garbage/validators.ts`:

- `assignmentInputSchema` — เหมือน `assignmentSchema` เดิมแต่**ไม่มี** `effectiveFrom`/`effectiveTo` (เซิร์ฟเวอร์เติมจาก baseline) ใช้กับ POST/PUT
- `routeUpdateSchema` — `name` (1–200), `needsVerification` (boolean), `stops` เป็นอาเรย์ของ `{ prevSeq: number | null, name, mode, roadId? }` ความยาว ≥ 1 · **ไม่รับ `seq`** เพราะเซิร์ฟเวอร์เป็นคนกำหนด
- ฟังก์ชัน pure `findOverlap(existing, candidate)` ใน `lib/garbage/overlap.ts` — คืนงานที่เวลาทับกัน (หรือ null) แยกออกมาเพื่อเทสได้โดยไม่ต้องมี DB · ต้องข้ามตัวเองตอน update (เทียบด้วย `_id`) และข้ามงานที่ `startMin`/`endMin` เป็น null (วันหยุด)

## UI หน้าแอดมิน

หน้า `/admin/garbage` เดิมมีแท็บ 7 วัน + ตาราง เพิ่มของใหม่:

- **ปุ่ม "+ เพิ่มงาน"** เหนือตารางของวันที่เลือก → `AssignmentFormModal`
- **ปุ่มแก้/ลบในแต่ละแถว** (ลบต้องยืนยันด้วย Swal พร้อมบอกว่าจะลบงานของรถคันไหน รอบไหน)
- **`AssignmentFormModal`** — เลือกรถ, รอบ, ชนิดงาน (ปกติ/แทนเบอร์/วันหยุด/พิเศษ), สาย, ช่วงเวลา, สายที่แทน, ป้ายกำกับ · ฟอร์มต้องซ่อน/ปิดช่องที่ชนิดงานนั้นไม่ใช้ (วันหยุด → ไม่มีสายและไม่มีเวลา) เพื่อไม่ให้ผู้ใช้ชนกฎ validator
- **`StopTimesEditor`** — ตั้งเวลารายจุดของงานที่เลือกสายแล้ว มีปุ่ม **"กระจายเวลาเท่ากัน"** (แบ่งช่วง start–end ให้จุดทั้งหมดเท่า ๆ กัน) แล้วปรับรายตัวได้ · จำเป็นเพราะสาย R1 มี 22 จุด กรอกมือทีละช่องคือทรมาน
- **`RouteManagerModal`** — เลือกสาย → แก้ชื่อ, เพิ่ม/ลบ/เลื่อนขึ้นลงรายการจุด, ติ๊ก "ตรวจสอบแล้ว" · ต้องเตือนให้ชัดก่อนบันทึกว่าการลบหรือสลับจุดจะกระทบเวลาของทุกงานที่ใช้สายนี้ (บอกจำนวนงานที่กระทบ)

ใช้ปุ่ม/อินพุตจาก `components/ui/adminTheme` และ `Swal` ตามธรรมเนียมฝั่งแอดมิน

## Error handling

- API คืน `{ error }` ทุกกรณี · 400 พร้อมข้อความไทยจาก zod หรือจากกฎข้ามเอกสาร (เช่น "รถ 5 มีงานรอบ 1 เวลา 4.00 – 5.10 น. อยู่แล้ว เวลาทับกัน")
- 409 เมื่อ `(weekday, truckNumber, shiftNo)` ซ้ำ (unique index ชน) พร้อมข้อความบอกว่าให้แก้งานเดิมแทนการเพิ่มใหม่
- 404 เมื่อ `[id]` หรือ `[code]` ไม่มีจริง
- ฟอร์มแสดง error ที่ตัวฟอร์ม ไม่ใช่ Swal เพียว ๆ (ผู้ใช้ต้องเห็นว่าช่องไหนผิดโดยไม่ต้องปิด dialog)
- ทุก mutation สำเร็จต้อง refetch สัปดาห์ใหม่ ไม่แก้ state ในเครื่องเอง (กันหน้าจอไม่ตรงกับ DB)

## ความเสี่ยงที่รู้ตัว

1. **เจ้าหน้าที่แก้ผิดแล้วกู้ไม่ได้ในหน้าจอ** — เลือกทับข้อมูลเดิมจึงไม่มี undo · บรรเทาด้วย audit log ที่เก็บ `before` (กู้ได้แต่ต้องให้คนมีสิทธิ์เข้า DB) และด้วยการยืนยันก่อนลบ · ถ้าใช้จริงแล้วพบว่าพลาดบ่อย ให้ทำ versioning UX รอบถัดไป (โครงข้อมูลรองรับอยู่แล้ว)
2. **การแก้รายการจุดกระทบหลายงานพร้อมกัน** — บรรเทาด้วยลำดับการเขียนที่ degrade แบบไม่แสดงเวลาผิด + เตือนจำนวนงานที่กระทบก่อนบันทึก + เทส pure function ครอบ
3. **การแก้พร้อมกันสองคน** — เดิมวางไว้ว่า "ไม่ทำ optimistic locking แล้วให้คนบันทึกทีหลังชนะ" แต่ระหว่างรีวิวพบว่ามีเคสที่ไม่ใช่แค่ "งานของอีกคนหาย" แต่**ข้อมูลผิดแบบไม่มีร่องรอย**: ถ้าอีกคน**สลับลำดับจุดของสาย**สำเร็จระหว่างที่ฟอร์มค้างอยู่ เซตของ `seq` ไม่เปลี่ยนเลย ด่านตรวจอื่นจึงผ่านหมด แล้วเวลาไปติดผิดจุดทุกจุด · จึงใส่ **optimistic lock ทั้งสองฝั่ง**: ทั้ง `PUT /routes/[code]` และ `PUT /assignments/[id]` บังคับให้ส่ง `updatedAt` ที่โหลดมา ไม่ตรง = **409** ให้ปิดฟอร์มแล้วเปิดใหม่ (`Route.updatedAt` / `Assignment.updatedAt`, เอกสารเก่าที่ยังไม่มีฟิลด์นี้จะข้ามการเทียบ) · POST ไม่ต้องมีเพราะยังไม่มีเอกสารให้ชน
4. **การชนกันแบบ "แก้ฟิลด์คนละตัวของงานเดียวกัน"** ยังเป็นแบบคนบันทึกทีหลังชนะ (ทั้งก้อน) — lock จับได้แค่ว่า "ข้อมูลเปลี่ยนไปแล้ว" ไม่ได้ merge ให้ · ยอมรับได้ที่ขนาดทีมนี้ (เจ้าหน้าที่ไม่กี่คน)
