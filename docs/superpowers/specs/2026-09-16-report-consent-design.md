## สถาปัตยกรรม: ขั้นที่ 0 ในหน้าเดิม

`pages/report.tsx` มี state machine อยู่แล้ว (`step: 1 | 2 | 3 | "success"`) — เพิ่มค่า `"consent"`
เป็นสถานะเริ่มต้นเมื่อยังไม่เคยยอมรับ

- ทางเข้าทุกทางถูกคุมด้วยโค้ดจุดเดียว ทั้ง `/report` (ปุ่ม "เริ่มแจ้งเรื่อง" บนหน้าแรก)
  และ `/report?category=<Prob_name>` (การ์ดหมวดใน `components/citizen/home/ServiceGrid.tsx`)
- ไม่มีจังหวะที่ wizard โผล่แวบก่อนถูกเด้งกลับ (ไม่ต้อง redirect ข้ามหน้า)
- **ไม่แตะ** `components/Layout.js` (route `/report` ถูกยกเว้น layout เดิมอยู่แล้ว)
- ไม่แยก route `/report/consent` เพราะหน้า `/report` ก็ยังต้องมีด่านกันคนบุ๊กมาร์กอยู่ดี
  กลายเป็นด่าน 2 ที่ ต้องพา `?category=` ข้ามหน้า และมีจังหวะกระพริบ

### ลำดับเหตุการณ์

1. เข้า `/report` → `step` เริ่มต้นเป็น `"checking"` ซึ่ง**ไม่วาดอะไรเลย** (localStorage อ่านฝั่ง
   เซิร์ฟเวอร์ไม่ได้ ถ้าเริ่มที่ `"consent"` คนที่เคยยอมรับแล้วจะเห็นจอข้อตกลงกระพริบ 1 เฟรม)
2. `useEffect` แรกบนเครื่องผู้ใช้อ่านค่าที่เก็บไว้แล้วตัดสินทันที
3. ถ้า `stored.version === CONSENT_VERSION` → ข้ามไปขั้น 1 (หรือขั้น 2 ถ้ามี `?category=` ที่ไม่ใช่หมวดบริการ) ตามพฤติกรรมเดิมทุกอย่าง
4. ถ้าไม่ตรง/ไม่มี/อ่านไม่ได้ → แสดงจอข้อตกลง
5. กด **ยอมรับ**: เขียนค่าลงเบราว์เซอร์ → ยิง log แบบ fire-and-forget → เข้าขั้น 1 หรือขั้น 2 ตามข้อ 3
6. กด **ไม่ยอมรับ**: เปิดแผ่นยืนยัน → ปุ่มม่วง "กลับไปยอมรับ" ปิดแผ่น · ปุ่มแดง "ยืนยันยกเลิกคำร้อง"
   ล้าง state ทั้งหมด (รวมหมวดที่ติดมาจาก query) แล้ว `router.replace("/")`
7. **ไม่บันทึกการปฏิเสธ** — เข้ามาใหม่ครั้งหน้าเจอหน้าข้อตกลงอีก

**การทำงานร่วมกับ `?category=`**: effect เดิมใน `pages/report.tsx` ที่อ่าน query แล้ว `setStep(2)`
ต้อง**ไม่ข้ามด่าน** — แก้ให้เก็บค่าหมวดไว้เสมอ แต่เลื่อนขั้นได้เฉพาะเมื่อผ่านข้อตกลงแล้ว
(ระหว่าง `"checking"` / `"consent"` ห้ามเซ็ต step เป็น 2)

## หลักฐานการยอมรับ 3 ชั้น

### ชั้นที่ 1 — เบราว์เซอร์ (ตัดสินว่าจะโชว์อีกไหม)

`localStorage` คีย์ `tk.report.consent` เก็บ JSON:

```json
{ "version": "1.0", "acceptedAt": "2026-09-16T02:31:00.000Z", "deviceId": "<uuid v4>" }
```

- `deviceId` สุ่มครั้งแรกด้วย `crypto.randomUUID()` (fallback เป็นสตริงสุ่มถ้าเบราว์เซอร์ไม่มี) —
  ใช้กันแถว log ซ้ำเท่านั้น **ไม่ผูกกับตัวบุคคล**
- `acceptedAt` เก็บเป็น ISO string (UTC) — เวลาแสดงผลต้อง format ด้วย `timeZone: "Asia/Bangkok"` เสมอ
- อ่าน/เขียนหุ้ม `try/catch` ทั้งหมด — โหมดส่วนตัวหรือเบราว์เซอร์ที่ปิด storage จะเห็นหน้าข้อตกลง
  ทุกครั้งแต่ยังกดยอมรับและแจ้งเรื่องได้ตามปกติ

### ชั้นที่ 2 — แนบไปกับเรื่องตอนส่ง

`buildComplaintPayload()` เพิ่มฟิลด์ `consent: { version, acceptedAt }` **เฉพาะเมื่อมีค่าครบ**
(ไม่ส่ง `deviceId` ขึ้นไปกับเรื่อง · ไม่มีค่า = ไม่ใส่คีย์นี้เลย เพื่อให้ payload ของเรื่องที่ไม่มีข้อมูล
ยินยอมเหมือนเดิมทุกไบต์ และเลี่ยงการยัด `null` ลง path ซ้อนของ mongoose)

เพิ่ม schema ฟิลด์เดียวกันใน **ทั้งสองไฟล์** ตามกติกา schema ซ้ำของโปรเจกต์ โดยห่อเป็น sub-schema
ที่ปิด `_id` (ถ้าใส่เป็น plain object ตรง ๆ mongoose จะแถม `_id` ให้ทุกเอกสาร):

```js
const ConsentSchema = new mongoose.Schema(
  { version: { type: String, default: '' }, acceptedAt: { type: Date, default: null } },
  { _id: false }
);
// ...
consent: { type: ConsentSchema, default: undefined },
```

- `models/Complaint.js` และ `models/SubmittedReport.js` (ชื่อ model เดียวกัน คนละไฟล์)
- ถ้าไม่มีค่า (เรื่องเก่า / ส่งจากช่องทางอื่น) ปล่อยว่าง — **ไม่ required**
- ไม่มีข้อมูลส่วนบุคคลในฟิลด์นี้ จึงไม่ต้องแก้ `.select()` ของ endpoint สาธารณะ
  แต่ผู้ทำต้องเช็กว่า endpoint ที่คืนทั้ง document ไม่พังจากฟิลด์ใหม่
- **ตรวจซ้ำฝั่งเซิร์ฟเวอร์** ที่ `pages/api/submittedreports/submit-report.js`: ข้อมูลยินยอมที่
  รูปแบบผิดถูกทิ้ง เลขฉบับที่เซิร์ฟเวอร์ไม่รู้จักถูกทิ้งทั้งก้อน (ไม่รู้ว่าผู้ใช้เห็นฉบับไหน)
  ส่วนเวลาที่เพี้ยนเกิน 2 วันถูกแทนด้วยเวลาเซิร์ฟเวอร์ (การยอมรับเกิดขึ้นจริง เสียแค่ความแม่นของเวลา)
  — ถ้าไม่กันชั้นนี้ `acceptedAt` ที่ cast เป็น Date ไม่ได้จะทำให้ **บันทึกเรื่องร้องเรียนทั้งเรื่องล้ม**

### ชั้นที่ 3 — log collection ใหม่

`POST /api/complaints/consent-log` เขียน collection `report_consent_logs`
(model `models/complaints/ReportConsentLog.js`)

| ฟิลด์ | ชนิด | หมายเหตุ |
| --- | --- | --- |
| `version` | String | เลขฉบับข้อตกลง |
| `acceptedAt` | Date | เวลาที่กดยอมรับ |
| `deviceId` | String | รหัสสุ่มจากเบราว์เซอร์ |
| `appId` | String | `NEXT_PUBLIC_APP_ID` ของ deployment |
| `createdAt` / `updatedAt` | Date | `timestamps: true` |

สัญญา API:

- `POST` เท่านั้น (เมธอดอื่นตอบ 405) · **ไม่มี GET สาธารณะ**
- header `x-app-id` ต้องตรงกับ `NEXT_PUBLIC_APP_ID` ไม่ตรง → 400 (หมายเหตุ: `submit-report` **ส่ง** header นี้แต่ไม่ได้ตรวจ — endpoint นี้เข้มกว่า อย่า "ปรับให้เหมือนกัน" โดยลดความเข้ม)
- body: `{ version, acceptedAt, deviceId }`
- ตรวจก่อนเขียน: `version` ต้องอยู่ใน `KNOWN_CONSENT_VERSIONS` (ประกาศใน `consentContent.js` ใช้ร่วมกันทั้งหน้าจอและ API) · `deviceId` ต้องเข้ารูป
  `/^[A-Za-z0-9-]{8,64}$/` · `acceptedAt` ต้อง parse ได้และห่างจากเวลาเซิร์ฟเวอร์ไม่เกิน 2 วัน
  ไม่งั้นใช้เวลาเซิร์ฟเวอร์แทน
- เขียนแบบ **upsert** ด้วยคีย์ `{ deviceId, version }` (unique index) — ยิงซ้ำได้แถวเดียว
- ตอบ `204` เมื่อสำเร็จ · ฝั่งหน้าจอยิงแบบ fire-and-forget ไม่บล็อกผู้ใช้ และ **ไม่ retry**
- กติกาเดียวเรื่องน้ำหนักหลักฐาน (อย่าเขียนสลับกันในไฟล์อื่น): **log ชั้นนี้คือหลักฐานหลัก**
  ส่วนสำเนาบนตัวเรื่อง (ชั้นที่ 2) เป็น best effort ถ้าผู้ใช้กดยอมรับแล้วไม่ส่งเรื่องต่อ และ log
  ยิงไม่ผ่านพอดี = ไม่มีหลักฐานรอบนั้น ซึ่งยอมรับได้ตามขอบเขตรอบนี้

> ⚠️ **ความเสี่ยงที่ยอมรับ**: endpoint นี้เขียนได้โดยไม่ต้องล็อกอิน (ผู้แจ้งไม่มีบัญชี) มีโอกาสถูกยิงขยะ
> ตัวลดผลกระทบคือเอกสารเล็กมาก · upsert ทับตัวเดิม · ไม่มีช่องอ่านสาธารณะ · ไม่เก็บ IP/user-agent
> ถ้าวันหนึ่งเจอ abuse จริง ค่อยเพิ่ม rate limit หรือปิด endpoint แล้วเหลือหลักฐานชั้นที่ 2

## การทดสอบ

**vitest (logic ล้วน — ตามแนวโมดูลอื่นในโปรเจกต์)**

- `shouldShowConsent`: ไม่มีค่าเก็บไว้ · JSON เสีย · เลขฉบับไม่ตรง · เลขฉบับตรง
- `validateConsentLog`: version ไม่รู้จัก · deviceId ผิดรูป · acceptedAt ในอนาคตไกล/อดีตไกล (ต้อง fallback เวลาเซิร์ฟเวอร์) · เคสถูกต้อง
- `buildComplaintPayload`: ฟิลด์เดิมครบเหมือนเดิมทุกตัว + มี `consent` · เคสไม่มีข้อมูล consent

**ตรวจด้วยตา**

- เปิด dev server **พอร์ตอื่น** (ไม่ใช่ 3000) แคปเทียบแบบทีละจอ แล้ว**ปิดทุกครั้งก่อนส่งมอบ**
  (ห้ามทิ้ง dev server ค้างใน working copy ของเจ้าของ และห้ามรัน `next build` ขณะ dev รันอยู่)
- เคสที่ต้องดู: เข้า `/report` ครั้งแรก · เลื่อนไม่ครบแล้วติ๊กไม่ได้ · ยอมรับแล้วเข้าขั้น 1 ·
  เข้าด้วย `?category=` แล้วยอมรับต้องไปขั้น 2 · กดไม่ยอมรับแล้วยืนยัน · เข้าใหม่ต้องไม่เจอข้อตกลงอีก
- **ไม่กดส่งเรื่องจริง** — เครื่อง dev ต่อ Mongo production และการส่งจะเด้งแจ้งเตือนเข้ากลุ่ม LINE เจ้าหน้าที่
  การทดสอบส่งจริงเป็นการตัดสินใจของเจ้าของโปรเจกต์
